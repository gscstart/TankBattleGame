## 2. 调研结论

### 2.1 原版 Battle City（1985 Namco）核心机制

来源：[Battle City — Wikipedia](https://en.wikipedia.org/wiki/Battle_City)（2025-05 修订版）

| 机制 | 原版 | 我们项目 | 差距 |
|------|------|----------|------|
| 关卡数 | **35 关** | 6 关 | 缺 29 关 |
| 网格尺寸 | 13×13 | 13×13 | ✓ 一致 |
| 合作模式 | **同屏双人 co-op** | 单人 | **❌ 缺失（P0）** |
| 内置关卡编辑器 | **有**（最早一批内置编辑器的游戏之一） | 无 | **❌ 缺失（P0）** |
| 道具类型 | 4 种（clock / shield / bomb / 3-star 升级） | 6 种 | ✓ 我们更丰富 |
| 敌人种类 | **4 种（按尺寸分级，最大需 4 发击杀）** | 3 tier（按颜色/速度/破钢墙） | 部分覆盖 |
| 红色闪光敌人 | 有（携带道具，被击杀掉落） | 无此机制 | **❌ 缺失** |
| 砖块子格破坏 | 有 | 有 | ✓ 一致 |
| 草丛/水/冰/钢 | 全有 | 全有 | ✓ 一致 |
| 自杀式失败 | **可击毁自己基地** | 敌人只能从基地打 | ✓ 简化（合理） |
| 道具掉率 | 红闪敌人 = 100% 必掉 | 任意敌人 25% 概率 | 设计差异 |

### 2.2 同类项目对比

GitHub 搜索 `battle+city+pygame` 共 23 个结果，按 star 排序前 5：

| 项目 | ⭐ | 特性亮点 |
|------|----|---------|
| tirinox/pybattlecity | 20 | 纯 Pygame、关卡配置、敌人 AI |
| awhitefox/pygame_tanks | 6 | 教育项目、OOP 教学 |
| YANGMOXI/TankBattleCity | 4 | 中文社区、网页版移植 |
| Movelocity/battle-city | 3 | **RL 训练环境**（用 pygame 模拟做强化学习） |
| frgonzalezb/Udemy_Battle_City | 2 | Udemy 课程配套 |

**观察**：
- 多数为 1-2 人学习项目，**没有显著超越原版的玩法创新**
- Movelocity 把它做成 **RL 训练环境** —— 这是一个有想象力的方向（AI 自我对战）
- itch.io 上的"The Battle City remake"用 **Unreal Engine 重制**（不是 Python）—— 反映"重制"是该类游戏的常规需求

### 2.3 itch.io 社区观察

`tag-battle-city` 免费游戏区有：
- "The Battle City remake" — 直接复刻
- "Tank game upgraded with modern Unreal Engine" — **现代引擎 + 原版机制**
- "Steel-Terror" — **Zelda + Battle City 混搭**（动作 RPG 化）

社区共同痛点：
- "It's like Battle City but you are alone and someone screwed up with the space-time flow" — **单人孤独感**
- "Who will win? Reason with bombs or the most intelligent tank?" — **AI 太弱**

## 3. 项目现状分析

### 3.1 优势（已具备）

- ✅ 干净的模块分层（entities / world / game / utils / settings）
- ✅ 状态机、碰撞、AABB、子步子弹移动、软吸附等核心机制稳定
- ✅ 10 项已修 Bug 文档化、7 项回归测试覆盖
- ✅ 13 条踩坑清单防止后续回退
- ✅ CJK 字体自动检测、程序化音效生成
- ✅ 视觉纯代码绘制、零外部资源依赖

### 3.2 痛点（与扩展相关的）

| 痛点 | 位置 | 后果 |
|------|------|------|
| `self.player` 散落 28 处直接访问 | `game/level.py`（grep 计数） | ~~加 P2 时需全局替换~~ **A1 已完成（见 §6.1）** |
| `Level.update()` 单函数约 200 行 | `game/level.py: update()` | 加新子系统会爆炸 |
| 关卡数据硬编码字符串 | `world/levels.py` | 加关需改 4 处（文档 + dict） |
| 排行榜 / 存档 / 成就 / 事件系统 | 不存在 | 长期粘性功能无基础 |
| 测试是手写 `if errors: exit(1)` | `tests/*.py` | 难接入 CI、覆盖率统计 |
| 玩家输入耦合在 `PlayerTank` | `entities/player.py` | 加手柄 / 改键位要改 entity |

### 3.3 可用扩展点（已有钩子）

- `entities/powerup.py` 的 `ALL_TYPES` / `TYPE_COLORS` / `_draw_icon` + `Level._apply_powerup` + `POWERUP_SOUND` —— 加新道具改 4 处
- `world/tile.py` 的 `blocks_tank/blocks_bullet/destructible/bullet_consumed` 4 属性 —— 加新瓦片改 4 处
- `entities/enemy.py` 的 `TIER_FIRE_COOLDOWN` / `TIER_SPEED_MULT` / `TIER_BREAKS_STEEL` —— 加新 tier 改 3 处
- `settings.LEVEL_DIFFICULTY` 数组 —— 加新关卡改 2 处
- `state.*` 状态机 —— 加新状态改 3 处（handle_events / update / draw）
- `utils/events.py` 的事件名常量 + `Level.update` 中的 publish 点 —— 加新事件改 2 处（常量 + 触发点），订阅方独立扩展无需改 Level

## 6. 实施路线图（3 阶段）

### 阶段 A — 基础设施（约 1-2 天）

**目标**：让后续扩展不再回退

| 任务 | 收益 | 改动文件 |
|------|------|----------|
| **A1**: `self.player` → `self.players: list[PlayerTank]` refactor | 解锁 P2、成就、事件 | `game/level.py` 15 处 ✅ **2026-06-27** |
| **A2**: 事件总线（`utils/events.py`） | 解锁成就、回放、CI 钩子 | 新文件 + 替换 5 处直接调用 ✅ **2026-06-27** |
| **A2**: 事件总线（`utils/events.py`） | 解锁成就、回放、CI 钩子 | 新文件 + 替换 5 处直接调用 |
| **A3**: `pytest` 框架 + GitHub Actions | 后续所有改动有保护网 | `tests/` 改写 + `.github/workflows/ci.yml` |
| **A4**: 输入抽象层（`game/input.py`） | 解锁手柄、键位重映射 | 新文件 + `PlayerTank.handle_event` |

**退出标准**：
- 现有 22 项测试在 pytest 下全过
- 1 玩家玩法行为不变
- `self.player` 引用数从 28 降到 0（全部改 `self.players[i]` 或遍历）
- **A1 实施说明**（2026-06-27）：`game/level.py` 28 处 `self.player` → `self.players[0]`（保留 `[0]` 索引保持 1 玩家行为完全不变）；2 处列表操作改用 `self.players` 整体（`other_tanks.extend(self.players)`、`self.players + self.enemies`）；`Game.handle_events` 改为 `for p in self.level.players: p.handle_event(event)`，P2 实施时不用再改这一处；测试文件 4 个共 55 处同步更新；文档同步：`docs/03` Game 字段表。
- **A2 实施说明**（2026-06-27）：新建 `utils/events.py`（publish-subscribe，同步触发，异常隔离），定义 6 个事件名常量（`ENTITY_KILLED`/`POWERUP_PICKED`/`BASE_HIT`/`BASE_DESTROYED`/`LEVEL_COMPLETED`/`LEVEL_FAILED`）；`game/level.py` 7 个关键点 publish（敌人击杀、道具拾取、基地被击中、基地被毁、关卡完成、3 处关卡失败），原直接调用 sound/score 行为不变；新增 `tests/test_events.py`（7 个测试用例：基本 publish、unsub、异常隔离、回调内 unsub、clear、空 publish、事件名常量），零 pygame 依赖跑得最快；文档同步：`docs/04` 新增 §4.5 events API 章节含 6 个事件 payload 表 + 触发点表，`docs/06` §3.3 扩展点加 events 钩子。

## 9. 结论与下一步

### 推荐起点

**先做 A1+A2+A3 阶段 A 全套**（1-2 天）—— 这是**最高杠杆的投入**，因为：
- 解锁 70% 的后续功能
- pytest 保护网让所有后续改动安全
- 不改变现有玩法，零风险

**接着做 B 阶段的可玩性 6 项**（2-3 天）—— 直接提升产品感：
- 红闪敌人 + 生存模式 + 排行榜 = 三件套
- i18n 一次到位省后续翻账

**最后做 C 阶段的 6 项**（3-5 天）—— 把项目从"复刻"变成"独立游戏"。

### 总投入估算

| 阶段 | 工时 | 累计 |
|------|------|------|
| A | 1-2 天 | 1-2 天 |
| B | 2-3 天 | 3-5 天 |
| C | 3-5 天 | 6-10 天 |
| D（可选） | 5+ 天 | 11+ 天 |

**到阶段 C 结束**，项目状态预期：
- 3500 行 → 6000-7000 行
- 22 测试 → 50+ 测试
- 6 关 → 15+ 关 + 生存模式
- 1 玩家 → 1-2 玩家

- 0 工具链 → pytest + CI + 回放

## 11. 地图尺寸扩展分析（待决策 #5）

### 11.1 当前基线

```python
# settings.py
SCREEN_W = 832         # 屏幕宽
SCREEN_H = 684         # HUD 60 + 地图 624
HUD_H = 60
TILE = 48              # 瓦片边长
GRID_W = GRID_H = 13   # 13×13
MAP_PIXEL_W = MAP_PIXEL_H = 624  # 13 × 48
MAP_X = (SCREEN_W - MAP_PIXEL_W) // 2 = 104  # 水平居中
BASE_GRID = (6, 12)    # 基地
```

**坦克 48×48 = 正好 1 个瓦片**，子弹 10×10。

### 11.2 性能影响实测（基于代码）

| 热点 | 算法 | 13×13 → 24×24 影响 |
|------|------|---------------------|
| `Tilemap.rect_collides_solid` | 扫 rect 覆盖格 | **不变**（坦克/子弹覆盖 1-2 格，与网格大小无关） |
| `Tilemap.rect_hits_brick_subcell` | 扫 rect 覆盖格 | **不变** |
| `Bullet.update` 子步 | `max(1, max(\|dx\|,\|dy\|)/2) + 1` | **不变**（子步按移动距离算，不按瓦片算） |
| `line_of_sight` | 扫两点间每格 | **1.85×**（13 → 24，最长距离翻 1.85 倍） |
| `Tilemap.tiles` 内存 | 13² → 24² | **3.4×**（169 → 576 个对象，仍 < 100 KB） |
| 同屏实体密度 | 玩家自然多放 | **+30~50%**（空间大了自然会塞更多，需要重新平衡 `LEVEL_DIFFICULTY`） |

**结论**：**性能不是瓶颈**，主要影响是**视觉**和**平衡**。

### 11.3 视觉权衡（屏幕固定 832×684）

| TILE | GRID | 瓦片面积 | 坦克大小 | 视觉感觉 |
|------|------|----------|----------|----------|
| 48 | 13×13 | 48²=2304 px² | 48×48（1×1 格）| 经典、坦克明显 |
| 40 | 15×15 | 40²=1600 px² | 40×40（1×1 格）| 略小、适中 |
| 36 | 17×17 | 36²=1296 px² | 36×36（1×1 格）| 现代感、内容密 |
| 30 | 21×21 | 30²=900 px² | 30×30（1×1 格）| 紧凑、快节奏 |
| 26 | 24×24 | 26²=676 px² | 26×26（1×1 格）| 像点阵、小屏 |

**关键约束**：
1. 坦克必须 = 1×1 瓦片（保证 48² 的比例 = 整格碰撞 + 整数步进）
2. 屏幕宽 = GRID_W × TILE + 2 × MAP_X（居中），高同理
3. 832 宽下 GRID_W × TILE ≤ 624 → 限制：TILE ≤ 624 / GRID_W

### 11.4 5 个候选方案

#### 方案 A — 维持 13×13（推荐基线）
```
TILE=48, GRID=13×13
```
- **改动量**：0
- **优势**：保持复刻、零风险、所有现有内容直接用
- **劣势**：空间拥挤（5 敌人 + 道具 + 子弹时有点挤）
- **适合**：本季度没空调整，专注核心功能

#### 方案 B — 小幅扩大 15×15
```
TILE=40, GRID=15×15, tank=40
```
- **改动量**：低（改 4 个常量 + 坦克 48→40 + 子弹位置重算 + 6 关重画/重生成）
- **优势**：空间 +33%，坦克仍清晰可辨
- **劣势**：脱离 Battle City 经典尺寸（虽然 1 格差不大）
- **实施成本**：~0.5 天

#### 方案 C — 中度扩大 17×17（**推荐**）
```
TILE=36, GRID=17×17, tank=36
```
- **改动量**：中（同上 + 关卡重新设计）
- **优势**：**与决策 #1（独立生命）协同**——双打时两人有空间不撞
- **优势**：**与决策 #2（生存关 7）协同**——生存模式需要更开阔空间
- **优势**：现代感强、关卡设计更丰富
- **劣势**：坦克视觉缩 25%（仍可玩）
- **实施成本**：~1 天

#### 方案 D — 大幅 24×24
```
TILE=26, GRID=24×24, tank=26
```
- **改动量**：高
- **优势**：空间最大、内容最密
- **劣势**：坦克像马赛克、子弹更难看清、瞄准困难
- **不推荐**

#### 方案 E — 滚动相机（13×13 视口 + 大逻辑地图）
```
视口固定 13×13, 逻辑地图可达 24×24+
相机跟随玩家 / 基地
```
- **改动量**：很高（~5 天，所有渲染加偏移、AI 跨屏、子弹跨界、line_of_sight 改逻辑坐标）
- **优势**：物理空间无限、最现代感
- **劣势**：实现复杂、bug 多发
- **状态**：本季度不建议（属于"阶段 D 长线方向"）

### 11.5 实施成本汇总

| 方案 | 常量改动 | 关卡数据 | 渲染 | AI / 子弹 | 合计 |
|------|----------|----------|------|-----------|------|
| A 维持 | 0 | 0 | 0 | 0 | **0** |
| B 15×15 | 4 | 程序化重生成 | 自动 | 速度/冷却微调 | **0.5 天** |
| **C 17×17** | **4** | **程序化重生成** | **自动** | **速度/冷却微调** | **1 天** |
| D 24×24 | 4 | 程序化重生成 | 自动 | 速度/冷却大幅调 | 1.5 天 |
| E 滚动 | 全部 | 重写 | 大改 | 大改 | 5+ 天 |

### 11.6 推荐

**选 C（17×17）**—— 理由：

1. **与 4 个已定决策强协同**：
   - #1 独立生命 → 17 格够两人不撞
   - #2 生存关 7 → 17 格给无尽模式更开阔
   - #3 程序化生成 → 17×17 网格的关卡数据用算法生成比手画容易（更多空间 = 更多组合）
2. **风险低**：和 13×13 差 4 格，几乎不破坏视觉习惯
3. **成本合理**：1 天完成，常量 + 关卡（程序化）+ 微调
4. **可逆**：如果玩起来不行，回退到 13×13 只是 4 个常量
5. **节奏更现代**：17×17 是现代复古重制常见尺寸（如 Open Battle City 变种）

**不选 D / E**：本季度不是时候，会拖累核心功能交付。

**不选 A**：如果你确实想"破除复刻感"，A 就没意义了——13×13 是 Battle City 标志。

### 11.7 17×17 实施细节（如选 C）

```python
# settings.py 改动
TILE = 36
GRID_W = 17
GRID_H = 17
MAP_PIXEL_W = GRID_W * TILE  # 612
MAP_PIXEL_H = GRID_H * TILE  # 612
MAP_X = (SCREEN_W - MAP_PIXEL_W) // 2  # 110
BASE_GRID = (8, 16)  # 居中底部，末行 GRID_H-1
PLAYER_SPAWN = (8 * TILE, 15 * TILE)  # 基地上一行 GRID_H-2
TANK_SIZE = 36
BULLET_SIZE = 8  # 等比缩
BULLET_SPEED = 320  # 像素/秒（保持原速，未按比例缩）
```

**TILEMAP 自动适配**（因为 `MAP_W = GRID_W * TILE` 全局算），`Tilemap.from_layout` 接 17 字符串即可。**关卡数据**用 `world/generator.py` 程序化生成（决策 #3）。

**测试影响**：`test_features.py` 假设 13×13，需要：
- 改 LEVEL_1~6 → 改 generator 输出的 17 字符串
- `screenshot_*.png` 重新生成
- 测试 `13 cols` 断言改 `17 cols`

**新增回归测试**：
- `test_grid_size.py`：断言 GRID_W/H 与 MAP_PIXEL_W/H 算术正确
- `test_generator.py`：跑 100 次生成器，确保都合法（有基地、玩家、出生点）

### 11.8 17×17 关卡设计提示

- 基地 (8, 16)（末行 GRID_H-1），玩家默认 (8, 15) 旁边（上一行 GRID_H-2）出生
- 敌人 3 个默认生成点 (0,0) / (8,0) / (16,0)
- 砖块墙保护基地用 5×3 大小而不是原来 3×3
- 路径宽度 1-2 格（坦克占 1 格，要留 1 格侧身空间）
- 可加"BOSS 房间"（中间 5×5 留空），决策 #5 关 6 BOSS 关可用
